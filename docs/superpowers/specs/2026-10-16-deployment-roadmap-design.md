# 06 · Docker 部署、运维与渐进开发路线

日期：2026-10-16

状态：待评审草案；尚未创建 Dockerfile / Compose 或迁移工程。

入口：[设计总览](2026-10-16-next-phase-design.md)

## 1. 首版部署形态

使用单台 Linux 服务器和 Docker Compose。容器化用于固定依赖、隔离运行和可回退发布；不会自动带来高可用、数据备份或零停机。

| 服务 | 职责 | 对公网 | 持久数据 |
| --- | --- | --- | --- |
| gateway | 建议 Caddy：TLS、同源代理、请求体限制 | 80 / 443 | 证书与配置数据 |
| web | Next.js standalone Node 服务 | 否 | 首版不依赖持久页面缓存 |
| api | FastAPI / Uvicorn，首版 1 个 worker | 否 | 媒体卷；业务数据写 DB |
| db | PostgreSQL | 否 | `pg_data` |
| migrate（一次性任务） | Alembic 数据库迁移 | 否 | 无；成功后退出 |

网关与 web / api 同处应用网络；api 与 db 使用内部数据网络，web 不加入数据库网络。媒体只由 api 读取并检查权限，不挂成网关公开静态目录。

Caddy 的自动 HTTPS 需要正确域名、可达的验证端口和持久证书数据，并非启动容器就能绕过 DNS / 网络条件。开发环境使用显式本地 HTTP 或受信任本地证书，不能把生产 TLS / Cookie 规则静默关闭。[Caddy 自动 HTTPS](https://caddyserver.com/docs/automatic-https)。

Caddy 默认配置不提供这里所需的业务速率限制。首版由 FastAPI 实施：登录失败限制放 PostgreSQL 短期安全表，搜索等轻量限制可放单 worker 内存；重启会重置后者，因此不把它当持久身份保证。扩容多 worker / 多实例前必须重新设计共享限流。

## 2. 镜像与配置原则

### Next.js

- 使用多阶段构建，锁定依赖，输出 standalone；生产不挂载源代码目录，也不启动 dev server。
- standalone 默认不会自动带上 `public` 与 `.next/static`，最终镜像要显式包含所需资源并做缺图检查。
- 镜像由 CI 构建，以提交 SHA 标记并记录不可变 digest；同一次发布使用同一份构建，不在生产重新构建另一个版本。
- `API_INTERNAL_URL` 仅服务端可见；浏览器 API 基址用相对 `/api/v1`。密码与内部服务地址不放入 `NEXT_PUBLIC_*`。
- 网关配置验证 Next.js 流式响应、导航和开发环境 WebSocket，不用整站粗暴响应缓存破坏页面协议。

### FastAPI

- 从受支持 Python 基础镜像构建自己的 API 镜像，不使用已弃用的旧 FastAPI 预打包镜像。
- 首版从单 worker 起步，连接池与图片并发按服务器资源设置上限；更多 worker 不等于自动更快。
- 容器用非 root 运行，媒体目录单独授予写权限；不使用 privileged、不挂 Docker socket。
- 不在每个 worker 启动时同时执行迁移；migrate 任务成功后才启动新 API。
- 只信任实际网关传来的代理头，不能把可从公网直连的任意 `X-Forwarded-*` 当作真实身份或协议。

### PostgreSQL 与 secrets

- 选择受支持稳定大版本，锁定镜像版本 / 摘要；大版本升级必须有独立迁移与恢复演练。
- 数据卷路径依据所选官方镜像版本验证，不复制跨大版本的旧 `PGDATA` 示例。
- 运行账号不是超级用户，迁移账号与运行账号分开；web 没有数据库凭据。
- secrets 通过限定服务可读取的文件注入；配置仓库不放真实密码。Compose secrets 是访问隔离，不等于加密磁盘，宿主机权限仍需保护。
- 宿主机防火墙只开放必要入口；不把 db 的 5432 或 API / web 开发端口映射到公网。

上述部署能力参见 [Next.js output](https://nextjs.org/docs/app/api-reference/config/next-config-js/output)、[FastAPI 容器文档](https://fastapi.tiangolo.com/deployment/docker/)、[PostgreSQL 官方镜像](https://hub.docker.com/_/postgres)、[Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)。

## 3. 健康检查与故障

- DB：`pg_isready` 判断进程可接受连接；这不证明应用 schema 已正确迁移。
- API：`/api/v1/health/live` 仅判断进程响应；`/api/v1/health/ready` 验证 DB 可用、schema 版本兼容及必要媒体目录可用。
- Web：提供不依赖 DB 的 `/healthz`，另外用公开内容请求做端到端冒烟测试。
- Compose 使用 `service_healthy` / `service_completed_successfully` 表达启动依赖，而不是把“容器正在运行”当成就绪。
- 依赖在运行中掉线时应用仍需超时、重连与错误页；`depends_on` 不是持续故障恢复系统。
- `unhealthy` 不会凭空获得自动修复；区分进程退出的 restart policy、就绪状态和需要人工处理的磁盘满 / 迁移失败。
- 健康端点只返回最小状态，不泄漏连接串、目录、数据库名或错误堆栈。

公开读操作后端不可用返回清楚的 503 提示。媒体处理失败不伪装为上传成功。现有手机音乐服务不因 API 临时故障被重建。

参考：[Compose 启动顺序](https://docs.docker.com/compose/how-tos/startup-order/)。

## 4. 素材与存储分层

| 类型 | 位置 | 管理方式 |
| --- | --- | --- |
| 已审核的图标、纹理、字体、主题剪影 | web 构建资源 | 随镜像版本化，保留来源 / 授权记录 |
| 站主上传照片及缩略图 | `media_data` | API 授权访问，独立备份 |
| 文章、动态、专题、会话等 | `pg_data` | 数据库迁移、逻辑备份 |
| 本地参考素材库 | 开发机仓库外 | 不进入生产镜像，不成为运行依赖 |
| 密码、会话配置、证书私钥 | 受限 secrets / 证书卷 | 不提交 Git，不写前端构建物 |

当前仓库已有游戏相关图像、字体与商业音频，过场视频目录则被忽略。部署前逐类核对许可和来源；现有“非商业”页脚不能替代授权。本组设计不判断某个素材已经获得完整再分发许可。

没有明确可用许可的资源应保持可替换、可关闭，使用自行创作或已获许可的版本；不把整套下载素材库复制进公开 Docker 镜像。此项是发布前检查，不在本次文档任务中删除或改写现有资源。

图片文件与 volume 不是备份。代码镜像也不包含生产上传照片，不能用重拉镜像代替恢复数据。

## 5. 备份与恢复设计

建议初始目标：RPO 24 小时、RTO 4 小时，分别表示可接受的数据回退量与恢复时间。这是待演练验证的目标，不是当前保证。

备份至少包含：

- PostgreSQL 逻辑备份，建议 `pg_dump` custom 格式，并记录数据库及迁移版本。
- 与该备份配套的媒体文件、清单与校验和。
- 镜像 digest、非秘密部署配置、管理员与数据库角色重建说明。
- 单独加密保管的必要 secrets；密钥不与加密备份放在同一公开位置。

一致性流程：短暂停止内容发布、编辑、上传与媒体清理 → 生成数据库一致性快照 → 复制媒体与清单 → 校验完整性 → 恢复写入。此时媒体对象键不可原地覆写；未来若要不停写备份，需另设计对象版本 / 快照协议。

备份每日一份，建议保留 7 份日备、4 份周备、3 份月备；至少一份加密保存在宿主机之外。备份任务使用宿主机定时器或独立运维流程，不在 API 容器内部偷偷启动 cron。

每月至少在隔离环境恢复一次：建立空 DB 与角色 → 恢复数据 → 恢复媒体 → 使用对应镜像启动 → 校验文章 / 动态 / 关系数量、所有被引用 ready 媒体及关键流程。数据库角色与授权需单独重建，不能假设单库 dump 包含完整集群身份配置。

从备份恢复到生产之前撤销旧会话，防止曾注销的会话因时间回退重新生效；确认时区、迁移版本和上传路径。演练不得连接生产数据库或覆盖生产卷。

恢复报告记录耗时、缺失对象和校验结果。只看到“备份命令退出 0”不能视为已经具备恢复能力。[PostgreSQL SQL Dump / Restore](https://www.postgresql.org/docs/current/backup-dump.html)。

## 6. 发布与回退

首版接受短维护窗口，不为个人站提前实现复杂蓝绿发布。

发布顺序：

1. CI 检查与构建镜像，记录 web / api digest 和 schema 版本。
2. 在预览环境验证，核对资源清单和兼容性。
3. 发布前做配套备份，启用内容写入维护状态。
4. 只运行一次兼容性迁移；失败则停止发布，不启动依赖新 schema 的服务。
5. 更新应用镜像，等待就绪并跑登录、列表、详情、上传 / 发布 / 撤回冒烟。
6. 确认正常再开放写入，记录发布结果和恢复点。

数据库变更尽量采用“先加新字段并兼容旧应用，再切换，最后另一次删除旧字段”。回退优先切回兼容的旧应用镜像；不自动执行可能丢数据的 downgrade。

若只能恢复旧 DB，需要明确这是数据回退、保留故障现场与新数据备份，并经站主确认。不能发现失败就悄悄覆盖数据库。

恢复旧静态站只可作为只读应急入口，不应一边用旧数据展示一边继续接受新后台写入。不要在生产维护流程中使用会删除数据卷的操作，例如 `down -v`。

## 7. 开发里程碑与停止条件

这些是验收导向的阶段，不是已经排定的工期。下一步只把一个里程碑拆成实现计划，避免同时重写全站和所有 App。

| 阶段 | 交付范围 | 达标后才能继续 | 暂不做 |
| --- | --- | --- | --- |
| M0 保存基线 | 当前工作区快照、页面 / 路由 / 素材清单、关键交互截图、旧测试记录 | 未提交问卷改动被单独保全，现有页面与入口均可复现 | 不先覆盖旧站 |
| M1 框架与手机宿主 | Next.js 布局、公开文章只读 API / DB 导入（含既有封面媒体）、本地 Compose、手机注册表、原有页面迁移 | 原入口可用，音乐持久，地图人群 / 顶部 Joker 正确，无重复 PJAX | 不做全部新应用或复杂后台 |
| M2 INS 图文闭环 | 管理登录、CSRF、媒体、动态草稿 / 发布 / 撤回、手机和独立页 | 两设备看到同一公开内容，草稿图不可读，冲突 / 失败有反馈 | 不做关注 / 真实用户间私信 / 公开点赞 |
| M3 异世界导航 | 一个真实专题、认知匹配、搜索、印象空间、专题管理、本机足迹 | 不熟悉 P5 也能到文章，撤回即时遵守公开规则，过场不串线 | 不做战斗、请求平台、任务系统 |
| M4 生产上线 | CI 镜像、TLS、权限、资源审计、配套备份与恢复、旧链接重定向 | 完成隔离恢复演练、公开泄漏测试与发布回退演练 | 不以“容器能启动”代替验收 |
| M5 按使用扩展 | 文章管理后台、公共留言、工具箱等逐个项目 | 每个模块都有真实需求和独立验收 | 不批量增加空图标 |

用户新提出的功能以 [07](2026-10-16-world-features-design.md) 和 [08](2026-10-16-character-messaging-design.md) 细化：M2 共享媒体后，可分批增加 COOP / 照片墙、作品与专题、放课后 / 手记、混合角色会话，再扩展问题记录与技能全书。它们可在预览环境按优先级推进；任一批公开生产发布都须满足 M4 条件，不要求凑齐所有功能再上线。M5 的早期例子不覆盖这些更明确的新需求。

角色会话的完成条件包括预设剧情与实际 AI 自由输入、返回剧情、会话隔离、预算上限、异常降级及原版 UI 对照；只有预设选项不算完整交付。模型供应商、费用预算和数据保留策略在接入前落实，本次设计不触发付费服务。新增私密日记、共享相册和会话后，补充权限与备份恢复测试。

M1 可再分为外壳与路由、公开数据读取、原页面适配三个小批次；完成一个再接下一个。新站先运行在独立本地端口 / 预览环境，保留现有 8000 端口静态预览作对照；本次不变更正在运行的服务器。

M2 和 M3 的发布 / 撤回都需要公开响应不使用共享缓存。若为性能后来加入缓存，必须把失效测试加入对应阶段。

## 8. 旧数据迁移规则

- `posts.js`：按 slug 幂等导入，保留标题、日期、分类、标签和 Markdown；初次导入后停止双写。
- `site.js`：拆出类型化站点配置，保留简介与地图地点映射；不把所有展示配置无必要地数据库化。
- `phone.js`：音量 / 曲目 / 暂停偏好兼容读取；不能因为换框架就自动开声。
- 本机留言与投票：不自动上传，不导入为公开用户内容或全站真实统计。若以后做导出 / 导入，需要用户主动操作和去重规则。
- 地图与问卷：稳定 ID 及已确认转场保留，文章新路由映射经过全量核对。
- 游戏剪影、字体和 Markdown 扩展：先验来源 / 授权与渲染安全，再决定复用，不因改 React 就丢失视觉与对话语法。

任何迁移脚本先 dry-run 输出差异与数量，重复执行不复制文章；不得从文本中不加隔离地执行仓库外脚本或访客提供的 HTML。

## 9. 验证矩阵

| 层 | 验证重点 |
| --- | --- |
| 旧测试基线 | 当前 `node --test tests/*.test.cjs`；迁移中保留有用的纯逻辑测试 |
| React 单元 / 组件 | 注册表、返回规则、音频单例、偏好迁移、应用错误边界 |
| FastAPI + PostgreSQL | 权限、分页、发布事务、If-Match、媒体引用、关键词匹配 |
| 浏览器端到端 | 手机 / 桌面、独立页 / 弹层、Back / Forward、转场来源、音乐不中断 |
| 安全 | 草稿各入口泄漏、CSRF、上传伪造、秘密构建泄漏、限流 |
| 容器 | 冷启动、DB 慢启动、API 重启、缺媒体、磁盘不足、配置缺失 |
| 运维 | 备份恢复、旧镜像回退、迁移失败、证书 / 域名配置 |

新增 Next.js 工程后才有其构建 / 类型 / 浏览器测试命令；不能在此刻用现有静态测试通过来证明未来架构已经正确。

性能先测量后下结论。可用 2 vCPU / 4 GiB 作为首轮测试预算，观察 SSR、图片处理、数据库与总 RSS，再决定实际服务器配置；这不是购买建议、容量承诺或最低配置保证。首版限制图片并发、单页条数、请求超时与日志大小。

运行时结构化日志包含 request ID、路径模板、耗时和状态；不记录 Cookie、密码、原始搜索条件。监测至少覆盖 5xx、磁盘剩余、容器内存 / 重启、备份最近成功时间，避免只检查首页在线。
